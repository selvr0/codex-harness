# 작업 순서 기록 (session-plan)

합의한 순서를 과제 폴더의 `docs/plan.md` 하나에 적음. 사용자는 이 파일을 에디터 탭에 열어 두고 지금 어디까지 왔는지 봄.

## 규칙

- **시작하기 전**: 할 일이 두 단계 이상이면 먼저 순서를 제안하고 물음
- **적는 때**: 사용자가 "이 순서로 하자"고 하거나, 제안한 순서에 동의했을 때만 적음. 혼자 세운 계획은 적지 않음
- **일하는 동안**: 단계를 시작하면 `진행`, 끝내면 `완료`로 바꿈. `진행`은 한 번에 하나만 둠
- **바꿀 때**: 사용자가 순서를 바꾸자고 하면 바꿈. 바꾸는 게 낫다고 보면 먼저 묻고, 동의하면 고침
- **단계를 더하거나 빼지 않음**: 사용자 말 없이 단계를 늘리거나 줄이지 않음
- **대화가 길어지거나 요약된 뒤**: 일을 이어 가기 전에 `docs/plan.md`를 다시 읽음

## 파일 모양

파일 전체를 매번 다시 씀. 맨 위 한 줄은 이 순서가 무엇을 위한 것인지 적음.

```markdown
# 작업 순서: 답변 연습 서비스 첫 버전

| # | 단계 | 상태 |
|---|---|---|
| 1 | 실무자 요구사항 정리 | 완료 |
| 2 | 화면 구성 합의 | 완료 |
| 3 | 답변 저장 API | 진행 |
|   | └ 3-1 저장 함수 + 단위 테스트 | 완료 |
|   | └ 3-2 API 연결 + 통합 테스트 | 진행 |
| 4 | e2e 확인 + 보고서 | 대기 |

## 바뀐 순서

- 10:42 4단계 앞에 "에러 문구 정리"를 넣자는 제안 → 사용자 동의로 추가
```

- 상태는 `대기` · `진행` · `완료` 세 가지만 씀
- 한 단계에 할 일이 여럿이면 `└ 3-1`처럼 하위 단계로 나눔
- 순서를 바꿨으면 `## 바뀐 순서`에 시각과 이유를 한 줄 남김

## 주의

- 에디터 탭이 파일 변경을 바로 다시 읽지 않으면, 사용자는 탭을 다시 열어 확인함
- 이 파일은 계획 문서로 제출물에 남음. 사실만 적음
