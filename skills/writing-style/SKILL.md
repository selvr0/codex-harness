# 문체 (writing-style)

## 1. 적용 대상

| 대상 | 말투 |
|---|---|
| **실무자에게 보내는 메시지** | 항상 존댓말. 묻는 것은 확실하게 물음 |
| **결과 문서, 보고서, README, 계획 문서** | 첫 문단 · 요청 · 마무리는 `~습니다`, 항목과 설명은 `~임` · `~함` · `~됨` |

## 2. 어미

- 확정된 사실은 단정함: `~했습니다`, `~임`, `~됨`
- **완곡 어미를 쓰지 않음**: `~것 같습니다`, `~듯합니다`, `~할 수도 있을 것 같은데`, `~해도 될까요?` 금지
- 질문은 묻는 것을 분명히 씀: `A와 B 중 어느 쪽입니까?`, `이 값의 기준은 무엇입니까?`, `○○이 맞습니까?`
- 요청은 `~해주세요`로 분명하게 씀. 돌려 말하지 않음
- 해요체(`~해요`, `~했어요`, `~예정이에요`) 금지
- 구어 동사 대신 정확한 동사를 씀: `봤습니다` → `확인했습니다`
- 모든 문장을 `~합니다`로 맞추지 않음. 존댓말은 읽는 사람에게 직접 말하는 문장(첫 문단, 요청, 마무리)에만 씀. 번호 붙은 절 안의 설명은 `~임` · `~함`

## 3. 구조

- 결론이나 상황을 한 줄로 먼저 씀. 그다음 배경 · 이유 → 결정 → 요청이나 다음 단계
- 서론을 끌지 않음. 바로 본론
- 항목이 여러 개면 번호(1. 2. 3.)나 불릿으로 나눔
- **항목마다 이름을 먼저 붙임**: `다시 찾으려면 직접 스크롤해야 함` ❌ → `**지난 답변 찾기**: 직접 스크롤해야 함` ✅. 이름만 훑어도 글 전체가 파악돼야 함
- 비교는 표로 씀. 변경 전 · 후 화면은 `| 변경 전 | 변경 후 |` 표 칸에 나란히 넣음
- 긴 글(절이 넷 이상)은 절 제목을 헤딩으로 올림. 소제목은 명사구로 씀 (`원인`, `구조`). 의문형(`왜 ~인가`)과 서술형(`~하는 이유`) 금지
- 순서 · 설명과 떨어진 덧붙임은 `> **참고**` 줄로 시작함
- 기능 안내는 첫 줄에 무엇을 했는지 쓰고, 첫 절에 왜 만들었는지(지금까지 어땠고 무엇을 바꿨는지)를 씀. 그다음 사용 방법
- 문제를 알릴 때는 언제 해결되는지와 그 전까지 쓸 방법을 같이 씀
- 새로 생긴 건지 원래 있던 건지 확인하고 씀. 원래 되던 기능에 "이제"를 쓰지 않음

## 4. 논리 전개

| 패턴 | 예 |
|---|---|
| 상황 → 따라서 이렇게 함 | `답변을 다시 듣는 기능이 없어서 연습 효과를 확인할 수 없음. 따라서 녹음 재생을 먼저 만듦` |
| 규칙에는 이유를 붙임 | `API 키는 환경변수로만 씀. 코드에 넣으면 제출물에 키가 남기 때문임` |
| 선택지 둘을 놓고 하나를 고름 | `방법은 두 가지임. 1. 서버에 저장 2. 브라우저에 저장. 여러 기기에서 봐야 하므로 1로 정함` |
| 기술 문제와 결정 문제를 가름 | `이 문제는 기술 문제가 아니라 우선순위 결정 사항임. 실무자 확인이 필요함` |
| 틀린 건 틀렸다고 씀 | `DB 확인 결과, 앞의 추론이 틀렸음` |

- 연결어는 `따라서`, `결과적으로`, `즉`, `->`. `그래서` 대신 `따라서`. `하지만`은 반전이 있을 때만
- 인과는 `->`로 이어 씀: `빈 값으로 저장 -> 0원으로 공개됨 -> 비공개로 바꾸게 고침`

## 5. 문장

- **사실 하나에 한 문장.** `~인데, ~해서, ~라서`로 사실 여러 개를 한 문장에 잇지 않음
  - ❌ `저장은 되는데, 목록 화면은 새로고침해야 보여서 실무자가 저장이 안 된 줄 알 수 있습니다.`
  - ✅ `저장은 됩니다. 하지만 목록 화면은 새로고침해야 보입니다. 따라서 실무자는 저장이 안 된 줄 알 수 있습니다.`
- 앞 문장과의 관계는 문장 맨 앞의 `따라서`, `하지만`으로 드러냄
- 문제 / 한계 / 할 일처럼 내용이 바뀌면 문단을 나눔
- 괄호로 부연을 문장 중간에 끼울 수 있음: `(제출 전 화면 기준)`
- 강조는 문장 안의 행동 · 핵심어만 굵게
- 이름 · 시간 · 상태값 · 파일 · 화면 이름은 백틱: `` `답변 제출` ``, `` `server.js` ``
- 문장 길이를 고르게 맞추지 않음. 긴 설명 옆에 한 단어짜리 항목이 있어도 그대로 둠

## 6. 용어

- **정의된 말을 씀.** 구어를 그대로 옮기지 않음: `지금` → `현재`, `돔` → `동작함`, `붙여놨음` → `연동해뒀음`, `건드리지 말 것` → `조작 금지`, `새는 것` → `노출되는 것`
- 같은 대상은 끝까지 같은 이름으로 부름
- 도구를 사람처럼 쓰지 않음: `브라우저가 모르는` → `브라우저 저장소에 없는`
- 위치 · 대상은 실제로 가리키는 곳으로 씀. `서버에 있음` 대신 `샌드박스의 /data 폴더에 있음`
- 처음 나오는 용어는 `관리 목록(state)`처럼 한 번 정의하고 이후 같은 말만 씀
- 확인하지 않은 경위는 쓰지 않음. 확인한 사실만 씀
- 제품 · 도구 이름은 영문 그대로 씀 (`Playwright`, `Codex`)
- **실무자가 개발자가 아니면 개발 용어를 풀어 씀**: `API 응답` → `화면에 돌아오는 결과`, `스키마` → `저장하는 항목`. 화면 · 메뉴 이름은 화면에 보이는 그대로 씀
- 개발 문서에서는 억지 한자어 대신 개발 용어를 씀: `증분 저장` → `diff만 저장`, `읽기 전용` → `read-only`
- **직역투 금지**: `엣지 케이스` → `예외 상황`, `커버리지` → `범위`, `발송 정상성 검증` → `발송 검증`, `이력 관리` → `변경 내역`. 동료에게 말로 했을 때 어색하면 쓰지 않음

## 7. 표기

- 기술 용어, 파일명, 값, 화면 이름은 백틱
- 강조할 항목은 `**볼드**`
- 참고 문서나 링크는 본문 아래에 붙임

## 8. 하지 않는 것

- 인사말, 서두, 빈말(`좋은 질문입니다`, `도움이 되셨길 바랍니다`)
- 자기반성 · 사과 문단. 실수는 한 줄로
- 계절 · 분위기 · 비유. `~과 같은 방식입니다`, `A는 남고 지우는 것은 B뿐입니다` 같은 비유 · 대조 구문
- 근거 없는 지시. 이유는 지시 뒤에 한 문장으로
- 격려로 글을 닫기. 마지막은 요청 · 링크 · 다음 단계
- 글마다 굵은 목적 문장(`이 목적은 ~위함입니다`). 새 규칙 · 결정을 알릴 때만 씀
- 내용이 많은 표, 항목이 전부 같은 구조인 목록. 표는 짧게, 길어지면 번호 목록
- 과한 이모지
- 확인한 것과 추측을 섞기. 확인 못 한 것은 "확인 안 함"이라고 씀

## 9. 글을 써 달라는 요청

- 본문만 씀. `아래처럼 보내시면 됩니다`, `다음과 같이 작성했습니다` 같은 머리말을 붙이지 않음
- 그대로 복사해 쓸 수 있는 완성본으로 냄
