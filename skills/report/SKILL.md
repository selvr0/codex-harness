# 확인 보고서 (report)

결과물은 `report.html` 파일 하나임. 캡처가 파일 안에 들어 있어서 이 파일만 열면 됨. 제출물에 같이 넣음.

## 규칙과 사례 먼저 읽기

보고서를 쓰기 전에 아래 `보고서 형식`과 [cases.md](./cases.md)를 처음부터 끝까지 읽음. 형식은 지킬 규칙이고, cases.md는 그 규칙이 생긴 지적과 고친 모양임.

규칙을 코드로 검사하지 않음. 판단이 필요한 규칙이 많기 때문임. 읽고 직접 대조함.

## 폴더

과제 폴더 안 `docs/report/<YYYYMMDD>-<주제>/`에 만듦.

```
docs/report/20261031-answer-submit/
├ img/           캡처 원본 (박스 없이 찍은 것)
├ report.json    보고서 내용
└ report.html    만든 결과
```

## 순서

1. **캡처**: `screenshot` 스킬로 찍어 `img/`에 둠
   - 변경 전·후 짝은 같은 화면 크기, 같은 데이터, 같은 스크롤 위치로 찍음
   - 필요한 부분만 보이게 화면 크기를 정함
2. **강조 좌표**: 강조할 요소는 찍을 때 `--locate <선택자>`로 좌표를 받음
   - 보고서에서는 박스를 이미지에 그리지 않음. 출력의 `located` 좌표를 `report.json`의 `boxes`에 `[x, y, 너비, 높이]`로 옮기면 HTML이 그림
   - 보고서 밖에서 박스 친 PNG가 따로 필요하면 같은 좌표로 `highlight` 스킬을 씀
3. **내용**: `report.json`을 씀. 구조는 `scripts/build-report.mjs` 맨 위 주석, 쓰는 모양은 아래 `보고서 형식`을 따름
4. **대조**: 보고서 형식 규칙을 위에서부터 하나씩 보며 `report.json`과 맞는지 확인하고 고침
5. **만들기**: `node <이 스킬 폴더>/scripts/build-report.mjs docs/report/<폴더>/report.json`
6. **확인**: 보고서 폴더를 `0.0.0.0`에 띄워 브라우저 미리보기로 열거나, `screenshot` 스킬로 `file://` 주소를 `--full`로 찍어 봄. 박스 위치와 좌우 짝이 맞는지 봄

설치 확인: `bash test/selftest.sh` (시험용 report.json으로 HTML을 만듦)

## 보고서 형식

모든 보고서에 지키는 규칙임. 규칙이 생긴 경위는 [cases.md](./cases.md)에 있음.

독자는 이번 작업과 확인을 전혀 모르는 상사임. 보고서만 읽고 무엇을 왜 어떻게 확인했는지 알 수 있어야 함.

### 독자

0-1. **테스트에서 한 일의 이름**: 실무자가 쓰는 업무 용어는 설명하지 않음. 용어 표도 만들지 않음 (`showTermsTable: false`). 설명할 것은 테스트에서 한 일에 붙인 이름(`[[처음 공개]]` 등)뿐이고, 묶음 앞 공통 영역에 간략한 한 줄 + 상세 표(대상 | 바꾼 값 | 목적)로 적음. 같은 이름을 `terms`에도 `{ text: ["저장: …", "한 일: …"], table }`로 넣어 두면 본문의 태그를 눌렀을 때 그 자리에서 뜻이 뜸

0-2. **공통 내용은 공통 영역에**: 여러 절이 같이 쓰는 데이터 변경은 특정 절 아래가 아니라 묶음 앞 설명(`partIntros`)에 둠. 데이터를 여러 번 나눠 바꿨으면 그 변경 표(변경 | 대상 | 바꾼 값 | 목적). 시간 순서 표는 만들지 않음

0-3. **절 설명(`text`)**: 배열로 한 줄에 사실 하나. `목적:` → `데이터:` · `한 일:` → `본 곳:` 순서. 결과만 적지 않음. 묶음 앞 설명(`partIntros.text`)도 배열로 씀. 문자열(문단)로 쓰면 한 줄 폭이 75자로 잘려 문장 중간에서 줄이 바뀜

0-4. **뜻 없는 문장 금지**: `아래 절들은 한 번의 확인에서 나온 결과임`처럼 읽어도 새로 아는 게 없는 문장은 쓰지 않음. `이번 확인에서`, `이번 작업으로`, `5건을 바꿈`처럼 무엇을 했는지 안 드러나는 말 대신 한 일을 바로 적음 (`공개 칸 1개를 비공개로, 최소 인원 2개 · 이용료 1개를 바꾸고 …`)

0-5. **뒤 절을 앞에서 가리키지 않음**: 요약 · 환경 · 용어 · 묶음 앞 설명 · 표의 칸 어디서든 `확인 결과 4번`, `관련 절`, `(아래 ○○ 표)`, `(창은 아래)`처럼 뒤에 나올 절 · 표 · 캡처를 가리키지 않음. 이미 지나온 절을 가리키는 것은 됨

### 맨 위

1. **요약(`lead`)**: 배열로 쓰고 한 줄에 큰 변경 하나. 기존과 달라진 결과만 적음. 한 줄을 빼도 작업 설명이 성립하면 그 줄은 세부라서 넣지 않음. 절 번호 · "아래 참고"처럼 다른 곳을 봐야 아는 말을 넣지 않음

2. **표 두 개**: `변경사항`(`changes`: 항목 | 변경 전 | 변경 후)과 `확인 결과`(`results` + `resultsHead: ["확인 항목", "되어야 하는 것", "결과"]`). 기능을 바꾸지 않은 작업이면 `changes`를 뺌

3. **번호**: 표마다 1부터 매김. 아래 절은 `part`로 `변경사항` · `확인 결과` 묶음을 나누고, 묶음 안에서 표와 같은 번호 · 같은 이름을 씀 (한 줄 = 한 절)

4. **환경(`env`)**: 변경 전 · 후 커밋, 확인 방법(브라우저를 몇 개 무슨 역할로 띄웠는지, DB 조회 · API 호출로 봤는지), 서버, DB, 계정, 테스트 날짜, 화면 크기

### 변경사항 절

5. 비교할 변경 전 상태가 있으면(예: 실무자 피드백을 반영하기 전 · 후) 같은 데이터로 같은 장면을 찍어 `compare`로 놓음. 확인 결과 절보다 앞에 둠. 처음 만든 기능이라 변경 전이 없으면 `compare` 없이 확인 결과로 보여 줌

5-1. **고친 동작은 핵심 상황을 찍음**: 버그를 고쳤으면 그 버그가 실제로 생기는 상황으로 고친 뒤 모습을 찍음. 비슷하지만 다른 상황으로 찍으면 화면이 기대와 달라 보여 헷갈림

6. 가로가 세로의 3배를 넘는 캡처는 `stack: true`로 위아래에 놓음

### 확인 결과 절

7. **표 열**: 모든 확인 결과 표는 `상황 | 대상 | 확인한 값 | 결과`로 같게 씀

8. **상황**: "어떤 상태의 데이터를 무엇으로 바꾸는지 / 무엇을 하는지"를 한 문장으로 (`공개 칸을 비공개로 변경`, `최소 4명인 칸에 3명 예약`). 상태 이름만(`공개 칸`) 적지 않음. 같은 상황의 줄은 상황 칸을 `null`로 합침

9. **대상**: 데이터 하나에 한 줄 (`A회의실 09:00`). 여러 대상을 한 줄에 묶지 않음. 표 · 접힌 상세 · 요청 본문 어디서든 `처음 변경 7개`, `나머지 6개`, `A회의실 09:00~11:00`처럼 개수 · 구간 · 나머지로 줄이지 않고 모두 적음. API 응답 목록도 항목마다 값을 적음

10. **확인한 값**: 바뀐 값은 `{ "from": "3명 이상", "to": "4명 필수" }`로 적음 (회색 칩 → 진한 칩). 바뀌지 않는 값(응답 코드 · 기록 메시지)은 그대로 적음. 절 첫 문장에 이 값을 어디서 봤는지(DB · 화면 · 응답) 적음. API 응답의 코드 값(`MIN_4`, `DISCOUNT` 등)은 그대로 두지 않고 우리말 뜻을 앞에 붙임 (`4명 필수(MIN_4)`, `할인가(DISCOUNT)`). 뜻은 코드에서 확인함

11. **결과**: `GREEN` · `RED`로 시작하는 배지. 설명은 필요할 때만 뒤에 붙임. `RED`에는 무엇이어야 했는지 적음 (`RED 4명 필수여야 함`). 확인 중 고친 문제는 `(고치기 전)` 줄을 `RED`, `(고친 뒤)` 줄을 `GREEN`으로 나눔. `정상` · `통과` · `있음`을 결과로 쓰지 않음

12. **조작**: 기능을 모르는 사람도 따라 할 수 있게 누른 순서대로 적음 (어느 칸을, 어떤 키를 누른 채). 단축키 · 기능 이름만 적지 않음

13. **테스트 데이터**: 모든 절에 접힌 상세(`details`)를 둠. 데이터 이름과 id, 바꾸기 전 값, 한 일, 바꾼 뒤 값(DB · 화면 · 응답), 보낸 요청, 남은 기록. 본 그대로만 적음

14. **자동 테스트**: 마지막 확인 결과 절에 이번 작업으로 추가 · 수정한 테스트를 이름 그대로 모두 적음. 보고서를 만들 때 지금 코드로 다시 돌린 결과를 적고, 돌리지 않았으면 `RED 돌리지 않음`

### 용어

15. 맨 위 표와 절 이름은 `변경사항` · `확인 결과`. 기존 동작은 `기존 방식`. 여러 번 나눠 한 작업은 `1차 변경` · `2차 변경`처럼 순번으로 부르지 않고 한 일을 나타내는 이름으로 부름 (`처음 공개` · `공개 뒤 수정`). 보고서 안에서 정한 이름은 `[[처음 공개]]`처럼 감싸서 이름 태그로 그림 (`처음 공개하면`처럼 동사로 쓴 곳은 감싸지 않음. `code` 칸 안은 태그가 안 그려지므로 감싸지 않음). `변경 전` · `변경 후`는 compare의 좌우 이름으로만 쓰고 수식어(단계 · 번호)를 붙이지 않음

16. 화살표(`→`)는 값 칩과 흐름(체크 → 창 → 저장)에만 씀. 한 칸에 변경 전과 후를 문장으로 같이 적지 않음

## 쓰는 말

- 결과 칸은 `GREEN` · `RED`로 시작하고, 본 값은 "확인한 값" 칸에 "없어짐", "404"처럼 본 그대로 적음
- 표에서 있음 · 없음을 비교하는 칸은 `있음` · `없음`으로 시작하게 적음. 채운 칩 · 점선 칩으로 그려져서 한눈에 나뉨. 설명은 뒤에 붙임 (예: `없음 (관리자는 아무 칸에나 만듦)`)
- 캡처 설명(`note`)은 그 캡처에서 볼 곳만 한 줄로 적음
- 가정과 확인한 것을 섞지 않음. 확인 못 한 것은 "확인 안 함"이라고 적음
- 문체는 `writing-style` 스킬을 따름
