## 3. 크래프톤이 보는 것

Cofa Probe를 만든 크래프톤 AI 프론티어 본부 구한모(PO)·조정석(엔지니어) 인터뷰, Probe로 실제 응시한 코파톤 참가 후기, 언론 기사를 바탕으로 정리함.

**(0) AI Literacy와 AI Native**

대회 페이지는 2차를 "AI Native 역량"을 보는 단계로 설명함 [확인]. 크래프톤 측은 이걸 AI Literacy와 구분함 (인터뷰 4:20).

| 구분 | AI Literacy | AI Native |
|---|---|---|
| 뜻 | 기존 워크플로 안에서 AI로 효율화하는 사람 | 워크플로 자체를 처음부터 다시 설계하는 사람 |
| 태도 | 하던 일을 AI로 조금 더 빠르게 | 의도가 분명하면 일을 다시 짜고, 필요하면 직접 만들어 해결 |

**(1) 평가 세 축**

| 축 | 보는 것 | 비고 |
|---|---|---|
| **기술** (결과물) | 실제로 돌아가는지, 요구사항 충족, 유지보수성, 품질 위험 | 소스코드·화면 스크린샷·실행 상태까지 보고 채점 |
| **의도** (AI 활용) | 목표 구체화, 문제·제약 정의, 작업 분해와 위임, 검증 루프 설계, 맥락 유지 | 코파톤 후기: **변별력이 가장 컸던 축** |
| **인지** (이해도) | AI 산출물의 동작과 위험 예측, 구조 이해, 판단 근거 설명 | 코파톤 후기: **참가자 전원이 가장 낮았던 축** |

- 코파톤 FDE 트랙에는 다른 사람이 이어서 작업할 수 있는지를 보는 `소통` 축이 하나 더 있었음. 2차에 있는지는 모름 [추론]

**(2) 핵심 일곱 가지**

1. **하루 같이 일해 보기**: "업무 역량을 보는 가장 좋은 방법은 하루 같이 일해 보는 것" (인터뷰). 시험이 아니라 업무로 대하는 게 맞음
2. **문제는 정의돼서 오지 않음**: 요구사항은 한 번에 알려 주지 않게, "게임처럼 하나씩 풀리게" 설계함 (인터뷰). 실무자 에이전트에게 **사소한 것부터** 묻는 사람이 점수가 잘 나옴. "제가 할 일 1, 2, 3을 알려 주세요"는 막혀 있음
3. **AI를 주도하기**: 과제 지시서를 복사해서 "해 줘" 하면 점수가 낮음 (인터뷰). 설계는 AI와 같이 정하고, 오래 걸리는 구현은 나눠서 맡기는 사람을 높게 봄
4. **요구사항에 맞는 만큼**: "범용적으로 잘 설계했지만, 우리 요구사항에 맞게 설계된 거냐? 아니죠" (인터뷰). AI의 오버엔지니어링을 조절하는 게 사람 몫임. 코파톤 README에도 "모든 필요를 구현할 필요는 없다. 무엇을 먼저 만들지 판단하고 현업과 합의하는 것도 과제의 일부"라고 적혀 있었음
5. **이해하고 설명하기**: 코파톤 1등은 상위 3명을 면접해서 **"왜 이렇게 했는지"**로 가림 (인터뷰). 확인 문제의 모범 답안 구조는 **내 코드의 약점 → 왜 위험한지 → 다음 개선 계획** (후기)
6. **적게 쓰고 잘하기**: "잘하시는 분들일수록 비용 적게 쓰시거든요" (인터뷰). "구현 다 끝내 놔" 하면 10분 만에 나오지만 고치느라 3시간 허덕일 수 있음
7. **작동하는 결과물과 근거**: 박재민 AI 프론티어 본부장 "AI와 함께 문제를 정의하고 근거를 확인하며 **결과를 끝까지 검증**하는 데서 경쟁력이 나온다" (기사). 영상 속 채점 기준에는 "변경 이유와 검증", "실패 상황의 이해" 항목이 따로 있었음

**(3) 같이 알아 둘 것**

- **기록이 곧 평가 자료**: 프롬프트, 도구 설정, 검증 실행 기록, 실무자 에이전트와의 대화, git 로그, 계획 문서를 수집함 (기사, 가이드). Codex에게 주는 지시문 자체가 채점됨
- **에고 버리기**: "코드를 사랑하는 사람은 뽑고 싶지 않다" (인터뷰). 남이 만든 좋은 스킬을 가져다 쓰는 것도 경쟁력으로 봄
- **SK하이닉스 언급**: 인터뷰에서 "SK하이닉스 AI 해커톤에서도 Probe를 솔루션으로 쓸 예정"이라고 직접 말함

## 4. 1차와 무엇이 다른지

1차(프로그래머스)와 2차(크래프톤 Cofa Probe)는 운영사가 달라서 시험 형식이 완전히 다름. 1차 후기를 2차에 그대로 쓰면 안 됨.

| 구분 | 1차 프로그래머스 | 2차 크래프톤 |
|---|---|---|
| 공통 | 문제 정의, 검증, 사용량보다 방식 | 같음 |
| 환경 | 채팅형 AI 어시스트 | 웹 IDE + Codex CLI |
| 결과물 | 판정과 답 입력 | **실제로 돌아가는 결과물** |
| 문제 | 문제가 주어짐 | **질문으로 요구사항을 끌어내야 함** |
| 과정 기록 | 채팅 대화 | 파일, 커밋, 터미널, 계획 문서까지 |
| 이해 확인 | 없음 | **AI 없이 답하는 후속 서술형** |
| 범위 판단 | 없음 | 무엇을 만들지 **스스로 정하고 합의** |

- 1차는 "주어진 문제를 AI로 정확히 푸는 사람"을, 2차는 "AI와 함께 일을 정의하고 끝까지 책임지는 사람"을 봄 [추론]
- 1차의 짧은 시간·30초 쿨다운·답이 흔들리는 AI도 결함이 아니라, 첫 지시를 설계하고 검증을 묶는 사람을 가려내는 장치였다고 봄. 2차의 불친절한 실무자 에이전트, 러프한 README, AI 금지 서술형도 같은 관점으로 읽으면 됨 [추론]

| ⑩ | 작업 표준서 질의응답 | 문서별 열람 권한, 최신판만 답해야 함 | 권한 밖·옛 판 내용을 답함 |

- 코파톤 후기에는 "README에 문제와 해결 방향이 이미 자세히 적혀 있었다"는 말도 있음. README가 러프한 경우와 자세한 경우를 **둘 다** 대비하는 게 맞음

**(4) 당일 알아 두면 좋은 용어**

| 용어 | 뜻 |
|---|---|
| 수율 | 만든 칩 중 합격한 비율 |

## 6. 작업 방식 [추론]

**(1) 데이터 먼저 의심하기**

받은 자료는 정답이 아니라 **조사 대상**으로 보는 게 맞음. README, 데이터, Codex 결과 모두 해당함. 크래프톤 AI R&D 해커톤(Cofa와 다른 대회)에서도 날짜 라벨이 일부 지워진 데이터를 줬고, 데이터를 먼저 살핀 참가자는 맞혔지만 바로 모델을 돌린 참가자는 **자신 있게 틀린 답**을 냈음.

- **확인할 것**: 파일 구성, 컬럼 뜻, 행 수·기간, 빈 값, 이상한 값, 중복, 단위·시각대(KST/UTC), 파일끼리 잇는 키
- **지시 예**: "이 CSV들의 컬럼, 행 수, 기간, 빈 값, 중복, 이상한 값을 요약해 줘. 파일끼리 어떤 컬럼으로 이을 수 있는지도 알려 줘. **아직 분석은 하지 마.**"
- **이상한 점을 찾으면**: 마음대로 고치지 않고 실무자에게 물어봄. 물을 수 없으면 가정을 정하고 문서에 적음
- **시간**: 처음 10분 안에 끝냄

크래프톤 측 표현으로는 에이전트를 **"현미경처럼"** 쓰는 것임. 보는 일은 AI에게 맡기고, 어디를 볼지는 사람이 정함.

**(2) 숨은 조건 찾기**

5절 시안표의 숨은 조건(가장자리 제외, 기준 변경 등)은 예시임. 실제 조건은 실무자 에이전트와 주고받으면서 알아내야 함. 다만 막연하게 묻는 게 아니라 **데이터에서 이상한 점을 먼저 찾고 그걸 근거로 묻는** 방식이 가장 강력함.

| 길 | 방법 | 예 |
|---|---|---|
| 데이터가 먼저 알려 줌 | 이상한 점을 발견 → 근거를 들고 물음 | 가장자리 칩이 전부 불합격 → "가장자리는 원래 분석에서 빼나요?" |
| 미리 정해 둔 질문 | 어떤 과제든 통하는 질문을 던짐 | "이 기간 중에 장비, 프로그램, 기준이 바뀐 적이 있나요?" |
| 문서에 이미 있음 | README·데이터 설명·컬럼 이름에서 단서를 찾음 | 버전 컬럼 값이 중간에 바뀜 |

어떤 과제든 통하는 질문:

- **범위·제외**: "분석에서 원래 빼는 데이터가 있나요?"
- **변경 이력**: "이 기간 중에 장비, 프로그램, 기준이 바뀐 적이 있나요?"
- **예외 처리**: "재작업이나 재테스트한 건은 어떻게 세나요?"
- **판정 기준**: "어느 정도면 문제라고 보나요? 숫자 기준이 있나요?"
- **사용자**: "이 결과는 누가, 언제, 얼마나 자주 보나요?"
- **지금 방식**: "지금은 이걸 어떻게 하고 계세요? 어디서 시간이 제일 많이 드나요?"
- **성공 기준**: "이게 되면 뭐가 좋아지나요?"

**업무 방식과 기준을 물어야 함.** "어떻게 만들면 되나요?"는 답을 안 해 줌 (영상 속 실무자 에이전트: "과제 수행 방법은 안내하기 어렵다"). 끝까지 모르는 조건은 가정을 정하고 판단 문서의 "남은 한계"에 적어 둠. 서술형에서 "이런 가정을 했고, 틀리면 이렇게 바뀐다"고 설명할 수 있음.

**(3) 180분 배분 (예시)**

| 시간 | 할 일 |
|---|---|
| 0~15분 | README·데이터를 Codex로 훑음. 특이점과 빠진 정보를 찾음 |
| 15~35분 | 실무자 에이전트에게 질문. 누가, 언제, 무엇이 불편한지, 성공 기준이 무엇인지 |
| 35~50분 | 만들 것과 **안 만들 것**, 성공 기준, 검증 방법을 정하고 실무자에게 확인받음 |
| 50~140분 | 작게 나눠 구현 → 바로 검증 → 커밋. 판정·계산은 고정 코드로, LLM은 해석에만 |
| 140~165분 | 미리보기로 실제 동작 확인. 판단·근거·검증 결과·남은 한계를 문서로 정리 |
| 165~180분 | 필수 파일과 저장 상태 확인 후 제출 |

- Codex가 도는 동안 문서를 쓰는 식으로 병렬로 움직이는 게 좋음 (가이드도 응답 시간을 고려한 위임을 평가한다고 함)

**(4) README에 제출 문서 지정이 없을 때**

README가 필수 문서를 정해 주면 그대로 따름. 정해 주지 않았을 때 쓸 수 있는 기본 묶음임.

| 문서 | 담을 내용 |
|---|---|
| 인터뷰 기록 | 실무자에게 물은 것과 답, 거기서 찾은 숨은 조건 |
| 계획 문서 | 문제 정의, 성공 기준, 만들 것과 안 만들 것, 검증 방법, 합의 내용 |
| 판단 문서 | 고른 구조와 이유, 버린 대안, 검증 결과, 남은 한계, 실패 시 동작 |

**(5) 후속 서술형 대비**

| 예상 질문 | 답의 구조 |
|---|---|
| 왜 이 구조와 방식을 골랐나 | 요구사항 → 대안 → 선택 이유 |
| 무엇을 안 만들었고 왜인가 | 범위 판단과 합의 내용 |
| 실패하거나 데이터가 이상하면 어떻게 되나 | **약점 → 위험 → 다음 계획** |
| 결과가 맞다는 걸 어떻게 확인했나 | 검증 방법과 결과 |
| 질문의 전제가 실제 구현과 다를 때 | 차이를 밝히고 내 작업을 설명 (가이드 문구) [확인] |

- 작업 중에 "왜 이렇게 했는지"를 한 줄씩 메모해 두면 문항당 5분 안에 답하기 쉬움

7. 공개 저장소 `git clone`이 되는지 (추가 항목)
8. 연습 과제 README에 제출 문서 요구가 어떻게 적혀 있는지 (추가 항목)
