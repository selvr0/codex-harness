# SK하이닉스 AI 해커톤 2026 2차 예선 관점 노트

- 작성일: 2026-10-31
- 용도: 2차 예선 현장에서 읽고, 과제를 본 뒤 그 과제에 맞는 작업 규칙·스킬을 바로 만들기 위한 **판단 기준**
- 이 노트에는 완성된 하네스나 코드가 없음. 현장에서 만들 때 쓸 관점과 재료만 있음

  - **[공식]** 대회 페이지, 주최 측 가이드·메일

**결론: SK하이닉스는 "스펙이 아니라 결과로 증명하는 AI 실행력"을 찾고, 크래프톤은 그걸 "AI에 끌려가지 않고 주도하는가"로 평가함. 따라서 2차에서는 반도체 현장 문제를 질문으로 정의하고, AI에게 통째로 맡기지 않고, 요구사항에 맞는 만큼 실제로 돌아가게 만들고, 그 판단을 스스로 설명할 수 있어야 함.**

## 1. SK하이닉스가 이 대회를 연 이유

### 1-1. 취지와 목적 [공식]

- 과거 경력만으로는 AI 활용 능력을 충분히 보여 줄 수 없다고 봄
- 따라서 정해진 스펙보다 **실제 업무 환경에서 AI를 도구로 쓰는 유연함과 실행력**을 평가함
- SK하이닉스 미래 전략의 중심에 AI가 있음
- 목적: AI와 함께 혁신을 이끌 인재를 찾음. 본선에서는 반도체 현장의 고민을 AI로 해결할 **"AI Expert"**를 선발함

### 1-2. 슬로건과 핵심 가치 [공식]

| 구분 | 내용 |
|---|---|
| 슬로건 | "조건 없는 도전, 오직 결과로 증명하는" / "AI와 함께, 혁신을 주도할" / "당신의 가능성을, 결과로 보여주세요" |
| **ZERO-BASE** | 학력·전공·연차·현재 직장과 무관. 논리적인 AI 활용 능력과 문제 해결 집요함만 봄 |
| **REAL BUSINESS** | 가상 시나리오가 아니라 SK하이닉스 현장 과제 |
| **SHOW & PROVE** | 말솜씨보다 실제로 작동하는 결과물 |

### 1-3. 찾는 인재상 [공식]

1. AI 트렌드에 민감하고, 새 도구를 업무에 적용하는 걸 즐기는 사람
2. 복잡한 문제를 AI로 분석해 직관적이고 최적화된 결과를 내는 사람
3. 연차·전공과 관계없이 실력으로 증명하고 싶은 누구나

- 페이지 문구: "이력서와 타이틀은 중요하지 않습니다"

### 1-4. 단계별로 보는 것 [공식]

| 단계 | 보는 것 | 평가 도구 |
|---|---|---|
| 1차 예선 | AI 기초 지식과 활용 역량 | 프로그래머스 |
| **2차 예선** | **AI Native 역량.** "데이터를 활용한 AI 문제 해결 미션". "AI와 함께 문제를 정의하고, 해결 방향을 고민하며, 아이디어를 실제 결과물로 구현" | **크래프톤 Cofa Probe** |
| 본선 (11/11) | 반도체 현장 고민을 AI로 해결. AI Expert 선발 | AI 평가 + SK하이닉스 현업·AI 전문가 + OpenAI·크래프톤 전문가 |

- 예선 평가 방향: 반도체 지식보다 AI 도구로 문제를 정의하고 해결하는 **과정**을 봄 [공식 FAQ]
- 부정행위는 AI 검증 시스템과 행동 로그로 감시함 [공식 FAQ]

## 2. 크래프톤이 평가하는 방식 (가장 중요)

### 2-1. 출발점

> "사람의 업무 역량을 보는 가장 효과적인 방식은 그 사람이랑 하루 정도 같이 일해 보는 것" [인터뷰 11:13]

- Probe는 코딩 테스트가 아니라 **AI를 쓰는 업무 역량 테스트**임 [인터뷰]
- 현업과 가장 비슷한 환경을 만들고, 그 안에서 일하는 과정을 모두 기록해 평가함 [인터뷰]
- 응시자 한 명을 **평가 에이전트 20개 이상이 병렬로** 지켜봄 [인터뷰 20:58]
- 결과물, 작업 기록, **제출 후 질의응답**을 함께 분석함. 좋은 결과를 만들었는지, AI에 일을 맡기고 방향을 조정했는지, 자기가 만든 결과를 이해하고 설명할 수 있는지를 봄 [인터뷰 영상 설명란]

### 2-1-1. AI Literacy와 AI Native

SK하이닉스가 2차에서 보겠다고 한 "AI Native 역량"을 크래프톤 측은 AI Literacy와 구분해서 설명함 [인터뷰 4:20].

| 구분 | AI Literacy | **AI Native** |
|---|---|---|
| 뜻 | **기존 워크플로 안에서** AI로 효율화하는 사람 | **워크플로 자체를 처음부터 다시 설계**하는 사람 |
| 아는 것 | AI 도구가 무엇인지, 어떻게 쓰는지에 대한 방법론 | 내 의도가 분명하면 이 일을 AI로 어떻게 다시 짤지 |
| 태도 | 지금 하던 일을 AI로 조금 더 빠르게 | "이 부분은 기존 도구를 안 쓰고 직접 만들어 해결할 수 있겠다" |
| 비유 (인터뷰) | - | 머스크처럼 제로 베이스(first principles)에서 시작 |

- 1차(프로그래머스)는 "AI 기초 지식 및 활용 역량", 2차는 "AI Native 역량"으로 대회 페이지가 단계를 나눔 [공식]. 1차가 Literacy 쪽에 가깝다면 2차는 Native를 보는 단계로 읽힘 [추론]
- 2차에 적용하면: 실무자가 지금 하는 방식을 그대로 자동화하는 데서 멈추지 않고, **"이 일을 처음부터 다시 짠다면"**을 묻는 게 Native 쪽임. 다만 범위는 실무자와 합의한 만큼만 [추론]

### 2-2. 응시 환경이 그 철학을 어떻게 구현하는지

| 장치 | 내용 | 무엇을 보려는 장치인지 [추론] |
|---|---|---|
| README 과제 | 역할 → 상황 → 현업의 요청(한두 문장) → 현업 파트너 → 과제 → 실행 환경 [인터뷰 화면] | 러프한 요청에서 문제를 스스로 정의하는지 |
| 업무 담당자(시나리오 에이전트) | 현업 담당자를 본뜬 에이전트. 일부러 불친절하고, 요구사항을 한 번에 안 알려 줌 [인터뷰] | 질문으로 숨은 요구사항과 맥락을 끌어내는지 |
| 웹 IDE + Codex CLI | 터미널에서 `codex`. 파일·터미널·브라우저 미리보기 [공식] | AI를 어떻게 지시하고 나누어 맡기는지 |
| 브라우저 미리보기 | 만든 서비스를 안에서 실행해 확인 [공식] | 실제로 돌아가는 결과물을 만드는지 |
| 기록 수집 | 프롬프트, 도구 설정, 검증 실행 기록, 실무자 대화, git 로그, 계획 문서 [기사][공식] | 과정 전체 |
| 후속 서술형 | 제출물과 작업 기록으로 즉석 생성. 문항당 5분, AI·복사 금지 [공식] | 만든 걸 스스로 이해하고 설명하는지 |

| 축 | 크래프톤 설명 | 세부 항목 (코파톤 기준) [후기] | 실측 [후기] |

- 세 축의 바탕은 **기술 부채·의도 부채·인지 부채** 개념 [인터뷰 24:50]
- 코파톤 FDE 트랙에는 **소통** 축(다른 사람이 이어서 작업할 수 있는지)이 하나 더 있었음. 인수인계 문서를 만든 참가자가 고득점 [후기]. 2차에 있는지는 모름
- 크래프톤 측 AI Native 정의: "제한된 자원 안에서 AI의 장점과 한계를 운용해 결과물을 잘 만드는 능력" [후기]

### 2-4. 채점 방식

| 항목 | 내용 | 출처 |
|---|---|---|
| 판정 근거 | 세부 역량마다 루브릭과 근거. **소스코드 위치**까지 붙임 | [인터뷰 29:00] |
| 실행 확인 | 프런트엔드는 화면 **스크린샷**, 내부 **실행 상태**까지 점검해 판정에 반영 | [인터뷰 29:20] |
| 기준 고정 | **기준과 점수 환산은 코드**, 맥락 판단이 필요한 정성 평가만 LLM 에이전트 | [기사] |
| 일관성 점검 (메타 하네스) | 같은 제출물을 여러 번 평가해 점수가 일정한지, 다른 답안을 구별하는지 점검 | [기사] |
| 신뢰도 근거 | 모델별로 과제를 풀게 하면 Opus 약 95점, Haiku 70점대, Sonnet 중간 → 일반 벤치마크와 같은 순서 | [인터뷰 29:50] |
| 리포트 | 점수, 판단 근거, 지원자별 면접 질문 | [인터뷰 영상 설명란] |

영상 속 평가자 화면에서 보인 항목 [인터뷰 화면, 코파톤 과제 기준]:

- 채점 기준 예: 요구사항 충족도 25 / 변경 이유와 검증 25 / 실패 상황의 이해 35
- 점수 구간: 90~100 / 76~89 / 60~75 / 60 미만
- 결과 예: 기술 84/100 (기능적 정확성 12/15, 요구사항 충족도 23/25), 의도 52/100 (AI 작업 범위 설정 14/25)
- 세부 판정 예: "대체 결과의 구분 안내 — 미충족 0/1점", 근거 문장 + 소스코드 근거 링크

### 2-6. 높게 보는 행동과 낮게 보는 행동 [추론, 2-5 기반]

| 높게 봄 | 낮게 봄 |
|---|---|
| 사소한 것부터 묻고 점점 구체화 | "할 일을 알려 달라", "어떻게 만들면 되나요" |
| 지시서를 따져 보고 구조를 같이 설계 | 지시서 붙여 넣고 "해 줘" |
| 작게 나눠 맡기고 바로 검증 | 한 번에 크게 맡기고 나중에 고침 |
| 요구사항에 맞는 만큼, 범위를 합의 | AI가 제안하는 기능을 다 넣음 |
| 판정·계산은 코드로 고정, 근거 표시 | 판단까지 LLM에 맡김 |
| 실행해서 확인하고 검증 흔적을 남김 | "될 것 같은" 상태로 제출 |
| 왜 그렇게 했는지 설명 가능 | AI가 만든 걸 설명 못 함 |
| 적은 토큰으로 해결 | 토큰을 많이 써서 밀어붙임 |

## 5. 현장에서 확인할 것

### 5-1. 시작 직후 (0~5분)

- README 전체를 읽음. 필수 제출 파일명이 있는지 확인
- `codex` 실행 → `/status`로 모델·권한, `/model`로 모델 확인
- 데이터 폴더와 파일 목록 확인
- 남은 시간과 제출 마지노선 계산 (14:00 − 서술형 약 30분 − 문제 준비 최대 10분)

### 5-2. 데이터를 볼 때 (5~15분)

- 파일 구성, 컬럼 뜻, 행 수·기간, 빈 값, 이상한 값, 중복, 단위·시각대, 파일끼리 잇는 키
- Codex에게는 "요약만 하고 **아직 분석하지 마**"라고 선을 그음
- 이상한 점 목록 = 실무자에게 물을 목록

### 5-3. 실무자에게 물을 때 (15~35분)

- 데이터에서 찾은 이상한 점을 근거로 물음
- 공통 질문: 원래 빼는 데이터 / 기간 중 바뀐 것 / 재작업·재테스트 처리 / 판정 기준 숫자 / 누가·언제·얼마나 자주 보는지 / 지금은 어떻게 하는지 / 성공 기준
- 해결 방법은 묻지 않음. 업무 방식과 기준을 물음
- 답은 바로 문서에 적음

### 5-4. 계획할 때 (35~50분)

- 문제 정의, 성공 기준, **만들 것과 안 만들 것**, 검증 방법을 정함
- 실무자에게 범위를 확인받고 합의 내용을 남김

### 5-5. 구현할 때 (50~140분)

- 작게 나눠 맡기고, 하나 끝날 때마다 실행·검증·커밋
- 판정·계산은 고정 코드, LLM은 해석·설명에만
- Codex가 요구사항에 없는 걸 만들면 끊음
- Codex가 도는 동안 문서를 씀
- 서버는 `0.0.0.0`에 바인딩. 미리보기로 확인
- 과제용 API 키는 환경변수로만 (코드에 쓰거나 커밋 금지)

### 5-6. 제출 직전 (140~180분)

- 미리보기로 실제 동작 확인
- 판단·근거·검증 결과·남은 한계가 문서에 있는지 확인
- 필수 파일 경로와 저장 상태 확인 → 제출 확정 (확정 후 수정 불가)

## 6. 현장에서 만들 것의 재료 [추론]

완성된 지침이 아니라 "이 상황이면 이런 규칙·스킬이 필요하다"는 연결만 적음. 과제를 본 뒤 Codex와 같이 만듦.

| 상황 | 만들 것 | 근거 (이 노트) |
|---|---|---|
| 과제를 처음 받음 | 이번 과제용 작업 규칙 파일 (요구사항, 금지 사항, 완료 기준) | 2-5 (2), 2-6 |
| 데이터가 여러 파일 | 데이터 점검 순서 (8가지 확인 항목, "아직 분석 금지") | 4-3, 5-2 |
| 실무자 대화가 길어짐 | 인터뷰 기록 틀 (질문, 답, 찾은 조건) | 2-5 (1), 5-3 |
| 범위를 정해야 함 | 계획 문서 틀 (성공 기준, 만들 것/안 만들 것, 합의) | 2-5 (3), 5-4 |
| Codex가 과하게 만들기 시작함 | "요구사항에 없는 기능 금지" 규칙, 변경 전 계획 승인 단계 | 2-5 (3), 4-4 |
| 판정·계산이 들어감 | 판정 규칙을 코드로 고정하고 결과를 원자료와 대조하는 검증 단계 | 2-4, 4-1 |
| 세션이 길어짐 | 작업 상태·결정 사항 인수인계 문서 | 4-2 |
| 제출 직전 | 요구사항 대조표 (항목별 충족·누락), 판단 문서 틀 (판단·근거·검증·한계) | 2-4, 5-6 |
| 서술형 대비 | 결정마다 "왜, 대안, 위험" 한 줄 메모 | 2-5 (5) |

현장 지시 예:

> "이 노트와 README를 읽고, 이번 과제에 맞는 작업 규칙 파일을 만들어 줘. 노트 4절의 함정 중 이 과제에 해당하는 걸 골라 반영하고, 6절에서 필요한 것만 골라 줘."
